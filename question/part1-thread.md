1. 프로세스와 쓰레드의 차이에 관해서 설명해주세요.

> 백명규
> 
> 프로세스와 쓰레드의 차이는 어떤 영역을 공유하고 있는 가가 다름.
> 프로세스 별로는 서로 공유하는 메모리 데이터가 없음. 
> 그래서 서로 다른 프로세스 간 컨텍스트 스위칭이 발생할 때 비용이 큰 이유가 메모리에 올려놓은 캐시를 활용하지 못하기 때문에 초반 캐시 미스나는 과정에서 디스크에서 데이터를 가져오기 때문임.
> 반면에 쓰레드는 코드 힙 데이터 영역은 공유하고 스택 영역에 대해서만 별도로 가짐 그래서 메모리를 공유해서 사용할 수 있어서 이전에 비해서 캐시 미스로 인한 오류가 적음.
> 
> ※ 여기에서 IPC 같은 거로 프로세스가 통신하게 된다와 같은 부분도 이야기를 하고 잘하면 소켓으로까지 끌고 갈 수도 있음.
> 프로세스 간의 데이터는 공유하지 않는데 어떻게 이동할 수 있을까에 대해서 말하면 관심을 가질 수도...?

2. 멀티프로세스 프로그래밍이랑 멀티쓰레드 프로그래밍은 어떤 차이가 있을까요?

> 백명규
> 
> 멀티 프로세스 프로그래밍은 공유하고 있는 영역이 사실상 거의 없기 때문에 별도의 IPC 등을 고려해서 소켓으로 통신을 하거나 공유 메모리 등을 놔두고 프로세스 간 데이터 교환에 있어서 조금 추가적인 비용이 발생한다.
> 대신 프로그래밍을 할 때 별도로 독립된 공간을 가지므로 한 프로세스의 장애가 다른 프로세스로 전파되지 않는다는 특징이 있다.
> 
> → 크롬 브라우저나 BGSAVE 같은 백그라운드 기반 Redis 영속성 관련 처리를 할 때 주로 사용
> 
> 반면에 멀티쓰레드 프로그래밍은 데이터 교환은 공유하는 영역이 있으니 편하고 비용도 크게 들지 않겠지만 한 쓰레드의 오류가 다른 쓰레드로 전파된다는 특성이 있다.
> 
> → 병렬 처리 용으로 주로 사용하는 거 같음.

3. 멀티쓰레드 처리 방식에 관해 설명해주시고 어떤 점들을 고려해볼 수 있는지 설명해주세요.

> 백명규
> 
> 멀티쓰레드 처리 방식은 프로그램의 실행과정에서 병렬성을 살리기 위해 작업을 비동기적으로 처리할 때 주로 사용을 합니다.
> 보통 작업마다 쓰레드를 생성하면 쓰레드 생성 비용이 추가적으로 계속 발생하니 미리 쓰레드 풀로 쓰레드 수를 한정 지어 만들어 놓는 방식을 활용합니다.
> 그러면 쓰레드 생성 비용과 쓰레드 개수가 무한정 늘어나는 현상을 막을 수 있습니다.
> 이 때 쓰레드 풀을 생성하더라도 조심해야 할 부분이 있는데, 작업 간의 서로 연관관계가 있을 때 쓰레드 풀 내부에서 작업이 돌며 대기하면서 발생하는 쓰레드 부족 데드락이 걸릴 수 있으므로 이 부분을 조심해야 합니다.
> 
> ※ 추가적으로 고민해볼 수 있는 사항은 작업을 분할해서 처리하는 경우에는 작업을 나누는 비용과 합치는 경우에 대해서도 생각을 해보아야 합니다.

4. 멀티쓰레드 방식으로 구현을 만들었던 경험에 관해서 설명해주세요.

> 백명규
> 
> 제가 프로젝트에서 사용했던 멀티쓰레드 경험은 이메일 처리 경험입니다.
> 스프링에서 HTTP 통신으로 인해 요청이 들어오면 톰캣에서의 쓰레드풀에 있는 쓰레드가 하나 잡혀 사용자의 요청을 처리하고 반환됩니다.
> 이 과정에서 이메일을 보내는 작업이 길었고, 저는 응답 속도를 개선하기 위해서 이메일 요청 처리의 결과는 나중에 보일 수 있도록
> 이메일 작업은 사용자의 요청 처리를 하는 쓰레드가 아닌 별도의 쓰레드풀로 작업을 이동시킨 뒤 처리하는 방식을 통해 요청 처리 쓰레드는 이메일 처리
> 응답을 기다리지 않게 함으로써 응답시간을 개선해본 적이 있습니다
