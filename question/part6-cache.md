1. CPU 캐시에 관해서 설명해주시겠어요?

> 백명규
> 
> CPU 내부에도 메모리 뿐만 아니라 그것보다 더 빠르게 필요로 하는 데이터에 접근하기 위해 L1, L2, L3  캐시와 같은 게 있음. 
> 설계마다 다르지만 L2나 L3에서는 보통 글로벌로 여러 코어가 공유하는 캐시로 두는 경우가 있고 L1의 경우에는 개별 코어로 가짐. 
> 이로 인해 빠르게 접근이 가능하다.

2. 멀티코어 시스템에서 캐싱으로 인한 문제점은 무엇인가요?

> 백명규
> 
> Cache Coherence Problem이라고 L1, L2 캐시는 코어 별로 공유하지 않고 독립적으로 동작해서 
> L1, L2 캐시에서 hit이 일어나 코어 간 데이터 동기화가 안돼서 실제랑 다른 값이 나오는 경우가 있다. 
> 그래서 이를 방지하는 방법은 Write-Through로 메모리까지 한꺼번에 바꿔버리는 방법이 있음. 
> 이건 조금 메모리 버스 등의 도움을 받는 방법이 있는데 이런 문제도 발생할 수 있다 정도만 알고 넘기면 될 듯.

3. 데이터 캐싱 전략에 관해서 설명해주시겠어요?

> 백명규
> 
> 쓰기엔 write through와 write back이 있습니다. 
> write through는 즉시 캐시에도 저장하고 캐시가 아닌 곳에도 이후에 저장하는 방식입니다. 
> 이 방법은 즉시 영속성의 디스크에 데이터를 저장하므로 안정성은 높아지나 단점은 쓰기 과정에서의 부하는 그대로 이라는 점입니다. 
> 반면 write back은 캐시에다가 저장만 하고 디스크에 즉시 동기화하지 않습니다. 따라서 안정성은 떨어지지만 성능적으로는 좋습니다.
> 
> 읽기엔 look aside 방식과 read through 방식이 있습니다. look aside 방식은 캐시에서 데이터를 읽고 없으면 DB에서 직접 조회하는 방식입니다. 
> 이는 캐시 서버가 다운되면 DB에서도 데이터를 찾아볼 수 있기 때문에 어느정도 장애에 대해서는 대응이 된다. 
> 반면 read through 방식은 캐시에서만 데이터를 읽고 없으면 DB에서 캐시에 데이터를 동기화하는 방식이다. 
> 이 때의 단점은 DB에서 조회해오는 과정에서의 latency에 대한 단점이 있다.
> 
> ※ 최근에 이런 질문을 받아봤는데, 뉘앙스를 조금 조심해야 될 듯. 최근에 사용한 ~~ 이런 식으로 갑자기 이야기가 들어온다면 위처럼 말하면 안됨.
> 그럴 때는 LRU, LFU, RANDOM 이런 페이지 교체 알고리즘 관련된 부분에 대해서 말하는 게 좋음.
> 보통은 LRU 말하고 Redis에서는 LRU에서 Approximate LRU를 사용한다. 그 이유는 LRU는 자원 많이 소모한다.
> 아니면, Second Chance나 Clock 같은 거 간단하게 설명하면 될 듯.

4. 프로젝트에 캐싱을 해보셨다면 어떤 전략으로 본인은 선택을 했고 이유는 무엇인가요?

> 백명규
> 
> 개인적으로 채팅 서버를 만들 때 write back과 look aside 방식을 사용했다. 
> write back을 사용한 이유는 채팅은 읽기랑 쓰기가 1대1이기 때문에 write through로 쓰면 디스크에 쓰는 정도가 너무 잦아진다. 
> 그래서 한번에 모아서 DB에 쓰기 요청할 수 있는 write back 방식을 선택했다. 
> 그리고 look aside는 캐시에 DB 데이터를 동기화 시킬 일이 없을 것 같고 최신 데이터만 저장하고 캐시쪽에 있는 데이터를 DB에 동기화하는 게 맞지 않을까 싶어 선택했다.
> 
> ※ 위의 것도 Redis를 Cache로 쓰건 할 떄 얼마 동안 캐싱되게 설정했고 한정된 메모리에서 어떤 상황이기 때문에 교체 알고리즘 어떻게 선택했다에 대해서 이야기를 하면 좋을 듯.
> 저런 말이 나왔을 때 내가 스터디땐 위처럼 말했지만 저건 채팅 관련된 서버 제안을 한 거고, 채팅도 약간 틀린 것 같음.
